# 用嵌套结构 + 双参数寻址，而不是平铺复合名

多系统 × 多环境的配置有两种表达方式：把 `order-dev` 这样的复合名作为单层键，或者用 `systems → instances` 两层嵌套。

我们选了**两层嵌套**，并且每个工具调用必须同时传 `system` 和 `env` 两个参数。

**为什么**：两个维度是正交的——系统数和环境数是独立相乘的。平铺复合名把这层结构压进字符串，代价是每个使用点都要自己拼接和拆分，命名约定成了隐式契约；一旦有人写成 `order_dev` 或 `order.prod`，就会出现「看起来能用但查不到」的问题。嵌套结构让配置的形状与真实的 2×N 矩阵一致，`list_instances` 也能直接按系统分组展示。

**为什么参数也要两个，而不是一个复合字符串**：如果工具接受 `instance: "order-prod"`，调用方仍要拼字符串，等于把配置层的隐式约定搬到调用层。两个参数让「系统」和「环境」在类型上就是分开的，错误信息可以精确到「未知环境 'prd'（系统 order 下可用：dev, prod）」。

**代价**：13 个工具的签名各多一个参数，调用比单参数啰嗦。考虑到这是给 AI 调用的工具、且 `remove_job` 这类操作不可恢复，显式寻址换来的安全性优先。

**被否掉的方案**：`switch_env` 式的当前实例状态。忘切回来的代价是在 prod 上删任务，而且这类错误没有撤销。有状态的寻址对定时任务调度器风险太高。

**另一个刻意的选择**：不设 `default` 目标。所有调用强制显式，避免「以为在查 dev，实际在查 prod」。
